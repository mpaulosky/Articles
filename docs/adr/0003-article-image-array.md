# Track inline article images as a structured `ArticleImage` array, not just markdown text

Article images are uploaded to `wwwroot/uploads/{guid}{ext}` and referenced only as markdown `![]()` links inside `Content`. No authoritative list of an article's images exists anywhere: `UploadedImageReferences` reverse-engineers which uploads are "in use" by regex-scanning `Content` for `/uploads/<fileName>` on every save, diffing old vs new content to find orphans to delete. We considered leaving this as-is, since the array would still need to be derived by parsing `Content` on every save — it can't be primary data while `Content` remains a free-text field users edit directly.

We decided the derived array is still worth persisting. Storing `Content` in a document database (MongoDB via `MongoDB.EntityFrameworkCore`) makes an embedded collection (`OwnsMany`) natural rather than requiring a join table, and a persisted, queryable list of `ArticleImage` (filename/url, size, mimetype, alt text, uploaded timestamp) enables things the regex scan cannot: querying "which articles use image X", surfacing alt text without re-parsing, and replacing the ad hoc regex diff with a single parse-and-replace of the array on every save. We scoped this to images only, not general file attachments (nothing else is attached to an article today), and named the type `ArticleImage` rather than `Attachment` to reflect that.

**Consequences**: `Article` gains an `ArticleImage` array populated by parsing `Content` on every save; `UploadedImageReferences`'s regex-scan-based orphan detection is replaced by reading this array instead of re-scanning `Content`. Existing articles need a one-time backfill migration to populate the array from their current `Content`, since the field won't exist on documents written before this change. If a future need arises for non-image attachments, that's a new, separately-scoped concept — don't widen `ArticleImage` to cover it.
