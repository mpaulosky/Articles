## Overview

Version 0.1.9 closes two gaps left by the previous seven releases: the v0.1.2-v0.1.8 blog
posts existed on disk but were never linked from any index, and the release workflow's
automated docs commit was still trying to push straight to `main`, which this repo's branch
protection rules reject.

## What's New

### Blog Index Backfill

- **PR #24**: Backfill release blogs v0.1.2-v0.1.8 and route release docs PR around branch
  protection
  - Linked the seven previously-orphaned release posts (PRs #17-#23) into
    `docs/blogs/README.md`'s table, category lists, and milestone summary
  - Refreshed the top-5 table in the root `README.md`
  - Refreshed the latest-posts list in `docs/index.html`, also fixing stale links left over
    from an earlier release that pointed at files which no longer exist

### Branch-Protected Docs Automation

- Reworked the "Commit and push docs updates" step in `squad-release.yml` so it:
  - commits the generated blog/index updates to a dedicated `docs/release-notes-pr-<n>`
    branch instead of `main`
  - opens a pull request for that branch via `gh pr create`
  - enables auto-merge on it via `gh pr merge --auto --squash`
  - titles the PR with a `[skip-release]` marker so the automated PR's own merge doesn't
    re-trigger a second release run
- Added a `Mark merged PR as release-eligible` gate that reads the merged PR's title for the
  `[skip-release]` marker and, when present, skips version bumping, tagging, and release
  creation entirely — the automated docs PR is docs-only and shouldn't mint its own release.

## Technical Details

### Why a PR instead of a direct push

`main` requires pull requests, so a bare `git push origin HEAD:main` from the workflow's
`GITHUB_TOKEN` is rejected by the repository's rules. The previous version of this step
detected that failure and warned that the docs commit was skipped; this version routes
around it properly by using the same branch-and-PR flow a human contributor would.

### A follow-up gate this surfaced

The first real run of this flow (triggered by PR #24's own merge) showed that opening a PR
with the default `GITHUB_TOKEN` also requires the repository setting **"Allow GitHub Actions
to create and approve pull requests"** to be enabled — without it, `gh pr create` fails with
`GitHub Actions is not permitted to create or approve pull requests`, even though the
workflow already declares `pull-requests: write`. That step has `continue-on-error: true`,
so the job reported success while silently dropping the auto-generated blog post for PR #24.
The setting has since been enabled, and the leftover `docs/release-notes-pr-24` branch (which
had been pushed but never became a PR) was deleted. This post is the manual backfill for the
post that step tried and failed to create.

## Impact

### For Documentation

- Every release from v0.0.1 through v0.1.9 is now discoverable from the blog indexes, not
  just present on disk
- The Contributing convention documented in `docs/blogs/README.md` ("add the post to this
  index," "update the main README top 5") is back in sync with reality

### For Release Automation

- The docs-commit step no longer silently no-ops against branch protection
- Future merges will open and auto-merge their own release-notes PR without manual
  intervention, now that the create-PR permission is enabled repo-wide
