# Auth0 Hosted-Login Bot/Anomaly-Detection Risk for Scripted Test Logins

Research for issue #157 (child of wayfinder #156), blocking ticket #158 (fixture design).

## Summary and recommendation (TL;DR)

Of Auth0's four Attack Protection signals, only **Bot Detection** is a real, plausible risk for this project's scenario (3 fixed test users, valid credentials, real Universal Login, GitHub Actions shared/rotating IPs plus stable local-dev IPs). Brute-Force Protection and Suspicious IP Throttling both key off **failed** login attempts / signup floods, so successful scripted logins with valid credentials should not trip them. Breached Password Detection only fires on credentials known to be leaked, which test-account passwords will not be if chosen sensibly. Bot Detection, by contrast, is a tenant-wide, ML/behavioral risk-scoring feature that can flag automated/headless traffic regardless of credential validity, and Auth0 has no per-connection or per-application toggle for it — it is all-or-nothing for a tenant, with only a manually maintained IP AllowList as an exception path. Auth0's own Support Center article on this exact scenario ("Automating UI Tests Without Bot Detection Challenges") recommends **using a dedicated, non-production Auth0 tenant with Bot Detection disabled for automated UI testing**, rather than trying to allowlist CI IPs (GitHub Actions runner IPs are not static, are shared across all GitHub customers, and Auth0's allowlist is capped at 100 IPs/CIDR ranges — allowlisting GitHub's published ranges is impractical and would weaken protection tenant-wide). **This is the recommended path for ticket #158**: point Web.E2E.Tests at a separate non-production Auth0 tenant/connection dedicated to E2E, with Bot Detection off (Brute-Force Protection and Suspicious IP Throttling can be left on, since valid logins won't trigger them). Rate limits on the Authentication API are not a practical concern at 3 logins per PR build.

## 1. What bot/anomaly-detection features exist on Universal Login

Auth0's **Attack Protection** suite ([auth0.com/docs/secure/attack-protection](https://auth0.com/docs/secure/attack-protection)) documents four layered signals:

- **Bot Detection** — "Triggers a CAPTCHA step when a login attempt comes from an IP suspected of use by a bot," using "a large amount of data and statistical models to identify patterns that signal when bursts of login, signup, or password reset traffic are likely from a bot or script" and examining "IP addresses associated with authentication attempts" for "a high likelihood of being part of a credential stuffing attack." ([auth0.com/docs/secure/attack-protection/bot-detection](https://auth0.com/docs/secure/attack-protection/bot-detection))
- **Brute-Force Protection** — "safeguards your tenant against attackers who use a single IP address to target a single user account." Signal: "Velocity of login attempts from an IP for a particular account." ([auth0.com/docs/secure/attack-protection/brute-force-protection](https://auth0.com/docs/secure/attack-protection/brute-force-protection))
- **Suspicious IP Throttling** — "blocks traffic from any IP address that rapidly attempts too many logins or signups." Signal: "Velocity of login attempts from an IP for any number of accounts against a tenant." ([auth0.com/docs/secure/attack-protection/suspicious-ip-throttling](https://auth0.com/docs/secure/attack-protection/suspicious-ip-throttling))
- **Breached Password Detection** — "tracks large security breaches that occur on major third-party sites" and blocks/notifies when a login uses credentials that appear in a known breach. ([auth0.com/docs/secure/attack-protection/breached-password-detection](https://auth0.com/docs/secure/attack-protection/breached-password-detection))

Defaults, per the docs:
- Brute-Force Protection: **enabled by default when a tenant is created**; threshold defaults to **10 incorrect login attempts**, configurable 1–100; applies tenant-wide, "to all users, including tenant administrators."
- Suspicious IP Throttling: **enabled by default when a tenant is created**; configurable max failed-login attempts/day and max signup attempts/minute (docs give an example: "a throttling rate of 100 means Auth0 grants a new attempt approximately every 15 minutes").
- Breached Password Detection: ships enabled on B2B/B2C **Professional and Enterprise** plans; without configured response actions any of these features run in **Monitoring mode** only (logs risk events, takes no blocking action).
- Bot Detection: the docs do not state a clear default-on/off for new tenants; it is configured under Dashboard > Security > Attack Protection > Bot Detection, and per community threads is effectively opt-in/plan-gated rather than universally on.

## 2. Which would plausibly trigger on legitimate, repeated, valid-credential scripted logins

- **Brute-Force Protection — low/no risk.** It counts **failed** attempts against a single account ("multiple failed attempts to log into a user account from a single IP address"). Successful logins with valid test-user credentials do not count toward this. ([brute-force-protection docs](https://auth0.com/docs/secure/attack-protection/brute-force-protection))
- **Suspicious IP Throttling — low risk in normal operation.** It activates on "a high number of signup attempts or failed login attempts" from one IP in a short window (responding with HTTP 429). Successful, valid logins are not the trigger condition. Risk only rises if a flaky test causes repeated failed attempts from the same shared CI IP, or if that IP's request volume (across all traffic hitting the tenant, not just yours) is already elevated. The docs describe this as tenant-scoped, not explicitly as a cross-tenant reputation signal — no evidence in Auth0's docs that Suspicious IP Throttling itself pools signal across unrelated Auth0 customers. ([suspicious-ip-throttling docs](https://auth0.com/docs/secure/attack-protection/suspicious-ip-throttling))
- **Breached Password Detection — no risk**, provided test-account passwords are not themselves breached/leaked passwords. It only blocks/flags credential pairs found in known third-party breach dumps; valid, non-breached passwords "pass through normally." ([breached-password-detection docs](https://auth0.com/docs/secure/attack-protection/breached-password-detection))
- **Bot Detection — the real risk.** This is the one signal that is explicitly about *how* the login traffic looks (IP reputation, request bursts, behavioral/fingerprint patterns), independent of whether the credentials are valid: "identifies suspicious bot traffic by analyzing patterns in login, signup, and password reset requests," flagging IPs with "a high likelihood of being part of a credential stuffing attack." A Playwright-driven headless/automated browser hitting Universal Login repeatedly — especially from a GitHub Actions shared IP range that other tenants' traffic (or actual attackers) may also have used — is exactly the shape of traffic this feature is built to catch, regardless of credential correctness. Auth0's docs do not disclose the exact ML/behavioral signals used (a documented limitation — the mechanism is intentionally opaque), which matches the issue's expectation. ([bot-detection docs](https://auth0.com/docs/secure/attack-protection/bot-detection))

Local dev machines (stable, non-shared, presumably clean-reputation IP) are low risk under all four signals. GitHub Actions runners raise Bot Detection risk specifically, since runner IP ranges are large, shared across all GitHub customers, and rotate.

## 3. Auth0's documented mitigations for automated/E2E testing

- **Bot Detection cannot be disabled per-connection or per-application.** It is a tenant-level switch: "Bot Detection... applies to all connections in your tenant" ([bot-detection docs](https://auth0.com/docs/secure/attack-protection/bot-detection)). Auth0's own Support Center confirms this directly for the testing use case: "Bot Detection is a tenant-level configuration that evaluates request risks based on IP addresses, headers, and behavioral patterns," and explicitly "does not support 'user allowlisting' or disabling the feature for specific client applications within the same tenant." ([support.auth0.com — Automating UI Tests Without Bot Detection Challenges](https://support.auth0.com/center/s/article/automating-ui-tests-without-bot-detection-challenges))
- **Auth0's stated recommendation for this exact scenario**: that same Support Center article's guidance is to **"use a dedicated development or testing tenant where Bot Detection is disabled to run automated UI tests."** This is Auth0's own documented answer to "how do I run automated UI tests against Universal Login without hitting Bot Detection."
- **IP AllowList exists, but is a tenant-wide bypass, capped at 100 entries, and documented as intended for automated tests as a secondary/partial mitigation**, not the primary one: "You can allow up to 100 discrete IP addresses and/or CIDR ranges (IPv4 or IPv6) to bypass Bot Detection by adding them to the IP AllowList field" ([bot-detection docs](https://auth0.com/docs/secure/attack-protection/bot-detection)); a related Support Center note ("Selective Use of Bot Detection") states "An IP Allowlist can now be configured to bypass Bot Detection for running automated tests." In practice this is impractical for GitHub-hosted runners: GitHub Actions runner IPs are drawn from large, published ranges shared by every GitHub Actions customer and rotate — they are not a fixed small set of CIDRs, would likely exceed sensible allowlist size, and allowlisting them would blunt Bot Detection for a huge swath of unrelated internet traffic, not just this project's CI.
- **Community confirmation of the CI pain point**: an Auth0 Community thread from a team running GitHub Actions CI reports the same problem this issue describes — CAPTCHA challenges blocking CI logins — and an Auth0 moderator's reply states plainly: **"we don't offer any specific guidance on bot detection when it comes to testing,"** confirming IP whitelisting is dashboard-only (no API) and impractical for GitHub's non-static runner IPs; the thread's only other suggestion was self-hosted runners with a static IP. ([community.auth0.com — Disable bot detection in test environments](https://community.auth0.com/t/disable-bot-detection-in-test-environments/95278))
- **Brute-Force Protection and Suspicious IP Throttling do support a documented IP AllowList / exemption mechanism** ("Login attempts originating from IP addresses on the IP AllowList are exempt from brute-force protection," useful e.g. "for users behind a proxy"; Suspicious IP Throttling allows exempting "up to 100 discrete IP addresses and/or CIDR ranges"), but per §2 these features are not expected to trigger on this workload anyway, so this mechanism is a secondary safety net at most, not the load-bearing fix.
- **ROPG note (for #158's context only, not a recommendation)**: Auth0's own docs position the Resource Owner Password Grant as the mechanism specifically designed to sidestep the hosted-login/CAPTCHA/bot-detection surface for machine-driven or highly automated flows, since it never touches Universal Login. The team has explicitly ruled this out in favor of real UI-driven login, so it is noted here only so #158 has the full picture of Auth0's "official" alternative.

## 4. Rate limits on the Authentication API

Auth0 maintains separate rate-limit policies for the **Authentication API** (used by end-user login, `/authorize`, `/usernamepassword/login`, `/co/authenticate`, `/oauth/token`, etc.) versus the **Management API** — these are documented as distinct systems with different scopes and limits. ([auth0.com/docs/troubleshoot/customer-support/operational-policies/rate-limit-policy](https://auth0.com/docs/troubleshoot/customer-support/operational-policies/rate-limit-policy))

Reported figures found via search (not independently confirmed against a fetched numeric table, since the rate-limit-configurations reference page did not return the underlying matrix content through automated fetch): a commonly cited **Free tenant global Authentication API limit is ~300 requests/minute**, and Enterprise tenants have a documented baseline (~100 RPS) with optional short-duration "Performance Burst" multipliers (2x/3x/4x) available for up to 48 hours/month. Limits vary further by tenant type (Production vs. Development/Staging) and plan tier, per the policy overview page.

**Assessment**: at "3 logins per PR build," even a modest cap of a few hundred requests/minute leaves enormous headroom — this workload is not remotely close to any documented Authentication API rate limit, on any plan tier. Rate limiting is not a practical constraint for this project's E2E design. (The one caveat: if CI ever parallelizes many concurrent PR builds against the same tenant, or retries aggressively on failure, it's worth keeping an eye on volume — but at the stated 1-per-role, up-to-3-per-build cadence, it is a non-issue.)

## Recommendation for ticket #158

**Provision a dedicated, non-production Auth0 tenant (or at minimum a dedicated non-production connection group, if the project's Auth0 setup already separates environments) for E2E testing, with Bot Detection turned off on that tenant, and leave Brute-Force Protection and Suspicious IP Throttling on their defaults.** This is Auth0's own documented answer to this exact scenario, not an improvised workaround, and it is the only mitigation that reliably works against GitHub Actions' rotating, shared runner IPs (an IP-allowlist approach is a dead end for GitHub-hosted runners specifically, per Auth0's own community guidance).

Concrete Dashboard-level steps for #158 to scope:
1. Create (or designate, if one already exists for dev/staging) a separate Auth0 tenant intended for non-production use, distinct from the tenant serving real users.
2. In that tenant: Dashboard > Security > Attack Protection > Bot Detection — turn the feature **off** (or leave unconfigured/in Monitoring mode, which never issues a CAPTCHA challenge). Leave Brute-Force Protection and Suspicious IP Throttling at their tenant-created defaults — they only fire on failed attempts, which valid scripted logins won't produce.
3. Create the 3 test users (Admin/Author/User roles) in that tenant's database connection, matching whatever role/claims setup the app already relies on.
4. Point the app's Auth0 configuration for local dev and CI E2E runs at this non-production tenant/domain (via environment-specific config/app settings), while production deployments continue to use the protected, real tenant untouched.
5. No code-level CAPTCHA-bypass, IP-allowlist-of-GitHub-ranges, or ROPG workaround is needed with this approach — the E2E tests can drive the real Universal Login UI end-to-end exactly as planned, and will simply never receive a Bot Detection CAPTCHA challenge because that feature is off for the tenant they're authenticating against.

This keeps the production tenant's Attack Protection fully intact (no weakening of real-user protection), avoids the impossible-to-maintain GitHub Actions IP-allowlist path, requires no ROPG, and matches Auth0's own published guidance for this exact "automated UI tests hitting Bot Detection" problem.
